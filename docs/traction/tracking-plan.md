Дата: 2026-10-25 · Автор: Growth Marketer · Статус: черновик для ревью Manager.
Задачи: VAL-02 (лендинг и рекламный тест), ENG-05 (воронка приложения и недельный дашборд).
Реализуют: Web Designer (лендинг), Developer (приложение и скрипт отчёта), Architect
(изменения в SPEC §15).

Язык документа русский (D-IR-01). Имена событий, целей и свойств на английском в

## 0. Общие правила

1. **Один источник истины.** События приложения — это SPEC §15 плюс `trip_driven_confirmed`
   (ENG-05). Новое событие или свойство появляется только через правку этого документа и
   SPEC §15 (§2.5).
2. **Имена.** Формат `объект_действие`, строчные буквы, `snake_case`. Значения свойств
   перечисляются заранее (§1.3, §2.4); свободный текст не передаётся.
3. **Без персональных данных** (152-ФЗ, D-IR-05, D-IR-06). Нигде (в событиях, параметрах
   целей, UTM, именах ссылок-приглашений) нет имён, телефонов, e-mail, адресов, текста
   поисковых запросов и точных координат. Метрика прямо просит не передавать
   идентифицирующие данные в параметрах визитов и посетителей, в UserID, полях форм и
   UTM-метках [M2]. В приложении есть только псевдонимный `device_id` (SPEC §15, §16).
4. **Время.** Все отметки времени переводятся в Europe/Moscow. Неделя — ISO-неделя,
   с понедельника 00:00 по воскресенье 23:59:59 МСК.
5. **Окна совпадают.** Числитель и знаменатель любой доли относятся к одному закрытому
   окну. Когорта, чьё окно ещё не закрылось, помечается «ожидает» и в долю не входит.
6. **Считает скрипт.** Все числа отчёта считает скрипт по сырым выгрузкам, вручную ничего
   не складывается. Скрипт входит в ENG-05 (владелец — Developer, спецификация — этот
   документ). Каждое ключевое число сверяется вторым способом (§3.5).
7. **Тестовые данные отдельно.** Сборки `debug` и `demo` шлют события в отдельный ключ
   API AppMetrica (или не шлют вовсе). Устройства команды исключаются по списку
   `device_id` в конфиге скрипта.

## 1. Лендинг: Яндекс Метрика

### 1.1 Счётчик

| Настройка | Значение | Кто |
| --- | --- | --- |
| Счётчик | `METRIKA_ID` — параметр конфига лендинга, счётчик создаёт CEO (D-IR-06) | CEO |
| Инициализация | `ym(METRIKA_ID, "init", {clickmap: true, trackLinks: true, accurateTrackBounce: true, webvisor: false})` | Web Designer |
| Вебвизор | **Выключен**, пока Legal не одобрит: записи сессий могут содержать введённые данные | — |
| `trackLinks` | Включён: Метрика сама считает переходы по внешним ссылкам, в том числе на `t.me`. Это вторая, независимая оценка `tg_click` для сверки (§1.7) | Web Designer |
| Цели | Пять целей типа «JavaScript-событие» с идентификаторами из §1.2. Идентификатор цели задаётся в настройках счётчика, вызов — `ym(ID, 'reachGoal', target, params)` [M1] | CEO создаёт, Growth Marketer проверяет |
| Важно | Чтобы параметры попали в отчёт, нужна отдельная JS-цель с этим идентификатором (не только внутри составной цели) [M1] | — |
| Связь с Директом | Счётчик подключается к кампаниям Директа, чтобы цели были видны в отчётах Директа | CEO |

### 1.2 Цели (события лендинга)

Каждая цель передаёт параметры визита (объект `params` в `reachGoal`, [M1]). Во всех целях
есть `variant` и `utm_source`.

| Цель (идентификатор) | Когда срабатывает | Параметры | Сколько раз | Зачем |
| --- | --- | --- | --- | --- |
| `page_view` | Один раз за загрузку, после того как вариант отрисован | `variant`, `utm_source`, `utm_campaign`, `utm_content` | 1 на загрузку страницы | Знаменатель V по вариантам (визиты с целью `page_view`) |
| `cta_click` | Клик по любой основной кнопке призыва, которая **не** ведёт сразу в Telegram (прокрутка к блоку подписки, раскрытие формы) | `variant`, `utm_source`, `cta_location` | Каждый клик | Какие блоки страницы работают |
| `tg_click` | Клик по ссылке в Telegram-канал (любой кнопке, ведущей на `t.me`) | `variant`, `utm_source`, `cta_location` | Каждый клик; в отчёте считаем **визиты** с целью | Числитель CR_tg, основа сверки подписок (`ad-test-plan.md` §8) |
| `faq_open` | Раскрытие вопроса FAQ | `variant`, `utm_source`, `faq_id` | Каждое раскрытие | Какие возражения волнуют людей |
| `form_submit` | **Только когда форма e-mail включена** после одобрения Legal (D-IR-05): успешная отправка, ответ сервера 2xx | `variant`, `utm_source`, `form` = `email_waitlist` | 1 на отправку | Второй канал листа ожидания. **Сам e-mail в Метрику не передаётся никогда** |

**Как отправлять `tg_click`.** Переход в Telegram уводит со страницы, и цель может не
успеть уйти. Вариант 1: вызвать `reachGoal` с `callback` и перейти по ссылке в нём, а через
300 мс перейти в любом случае. Вариант 2: открыть ссылку в новой вкладке
(`target="_blank" rel="noopener"`). Выбирает Web Designer, работу проверяем по §1.7.

Пример (справочно, для Web Designer):

```js
ym(METRIKA_ID, 'reachGoal', 'tg_click', {
  variant: 'b',            // отрисованный вариант: a | b | c
  utm_source: 'yandex',    // из белого списка §1.3, иначе 'other' или 'none'
  cta_location: 'hero'     // hero | middle | final | sticky
});
```

### 1.3 Значения параметров

| Параметр | Допустимые значения | Правило |
| --- | --- | --- |
| `variant` | `a`, `b`, `c` | **Отрисованный** вариант, а не тот, что запрошен. Если `?v=` нет или он неверный, лендинг показывает вариант по умолчанию (решает Web Designer), и передаётся именно он |
| `utm_source` | `yandex`, `vk`, `telegram`, `interview`, `community`, `none` (меток нет), `other` (неизвестный источник) | Белый список. Всё, чего в нём нет, передаётся как `other`, так что случайная или чужая метка не попадёт в параметры как есть |
| `utm_campaign`, `utm_content` | По §1.5; вне шаблона — `other` | Проверка регуляркой `^[a-z0-9]+(-[a-z0-9]+)*$` |
| `cta_location` | `hero`, `middle`, `final`, `sticky` | Web Designer сверяет с разделами страницы; новое значение добавляется сюда |
| `faq_id` | `q1` … `qN` по порядку вопросов на странице | Текст вопроса не передаётся |
| `form` | `email_waitlist` | — |

### 1.4 Что считаем по лендингу

- **V** (визиты варианта) = визиты с целью `page_view`, где `variant` = X и UTM ячейки.
- **C** (намерение) = визиты с целью `tg_click`, те же фильтры.
- **CR_tg** = C / V за одно и то же окно.
- Формулы цены подписки и сверки с Telegram описаны в `ad-test-plan.md` §8.

### 1.5 UTM-метки

**Правила:** только строчные латинские буквы и цифры, слова через дефис (`-`); без пробелов,
подчёркиваний, кириллицы и `+`; одно написание на каждый источник; **никаких персональных
данных**; ссылку проверяем живым кликом до запуска. Исключение одно: `utm_term={keyword}` в
Директе подставляет сама площадка, и там может быть кириллица.

| Канал | `utm_source` | `utm_medium` | `utm_campaign` | `utm_content` | `utm_term` |
| --- | --- | --- | --- | --- | --- |
| Яндекс Директ (VAL-02) | `yandex` | `cpc` | `val02-promise-<гггг-мм>` | `a` / `b` / `c` (= вариант) | `{keyword}` (по желанию, синтаксис проверить в кабинете) |
| VK Реклама (VAL-02) | `vk` | `cpc` | `val02-promise-<гггг-мм>` | `a` / `b` / `c` | — |
| Пост в собственном Telegram-канале | `telegram` | `owned` | `channel-post-<гггг-мм-дд>` | вариант, если ссылка на конкретный | — |
| Интервью VAL-01 (ссылка после интервью) | `interview` | `referral` | `val01-interviews` | вариант | — |
| Сообщества, где админ разрешил ссылку | `community` | `community` | `<сообщество>-<гггг-мм>` (латиницей, без персональных данных) | вариант | — |

Параметр `?v=` управляет показом, `utm_content` дублирует его для отчётов Метрики. Они
должны совпадать; если нет, в отчёт идёт отрисованный `variant` (§1.3).

Пример: `https://<домен>/?v=a&utm_source=vk&utm_medium=cpc&utm_campaign=val02-promise-2026-11&utm_content=a`

### 1.6 Персональные данные: запреты

- Ни в одну цель, параметр или UTM не передаются e-mail, телефон, имя, никнейм в Telegram,
  IP, точная геолокация и текст, введённый пользователем.
- Форма e-mail выключена до одобрения Legal (D-IR-05). Когда её включат, в Метрику уходит
  только факт отправки (`form_submit`).
- Вебвизор выключен (§1.1).
- Имена ссылок-приглашений в Telegram только служебные (`val02-vk-a`), без имён людей.

### 1.7 Проверка перед запуском (до любых трат)

| # | Проверка | Как | Норма |
| --- | --- | --- | --- |
| 1 | Каждая из 6 рекламных ссылок открывает нужный вариант | Живой клик по каждой ссылке из `ad-test-plan.md` §5.5 | Видны заголовок варианта и UTM в адресе |
| 2 | Цели приходят с параметрами | Режим отладки Метрики (параметр `_ym_debug=1` в адресе; проверить в справке на дату проверки) и отчёт «Конверсии» → «Параметры визитов» | 5 целей; `variant` и `utm_source` верные |
| 3 | `tg_click` отправляется до перехода | 10 кликов по кнопке Telegram с телефона Android и с компьютера | Не меньше 9 из 10 в Метрике |
| 4 | Ссылка Telegram соответствует ячейке | Для каждой ячейки клик → в Telegram открывается ссылка-приглашение с нужным именем (способ A, `ad-test-plan.md` §8.2) | 6 из 6 |
| 5 | Неизвестный `utm_source` → `other`, без меток → `none` | Открыть `?utm_source=Test%20User` и страницу без меток | `other` и `none` |
| 6 | Нет персональных данных | Просмотр всех параметров в отладке | Только значения из §1.3 |
| 7 | Сверка `trackLinks` | Переходы на `t.me` в отчёте «Внешние ссылки» против визитов с `tg_click` | Расхождение не больше 10 % |

## 2. Приложение: события AppMetrica (SPEC §15 + ENG-05)

### 2.1 Общие свойства каждого события

| Свойство | Тип | Значение |
| --- | --- | --- |
| `device_id` | string | Псевдонимный ID устройства в AppMetrica (SPEC §15). Не связывается с людьми |
| `app_version` | string | `versionName` |
| `trip_id` | string | Если событие относится к поездке |
| время события | timestamp | Ставит SDK; для отчётов переводится в МСК |

### 2.2 Таблица событий

Свойства из SPEC §15 записаны в `snake_case`. Правила триггеров — это определение данного
плана; Developer реализует их буквально.

| Событие | Триггер | Свойства | Вопрос, на который отвечает (SPEC §15) |
| --- | --- | --- | --- |

| `ready_route_shown` | Список готовых маршрутов отрисован на «Лобовом стекле»; 1 раз за показ экрана | `count`: int; `start_city`: город (не координаты) | Покрытие готовыми маршрутами |
| `ready_route_selected` | Нажатие на строку готового маршрута | `route_id`; `rank`: 1… | Какие шаблоны привлекают |
| `search_started` | Первый запрос подсказок за один показ «Навигатора» | `query_len`: int | Использование свободного поиска |
| `search_selected` | Выбор подсказки | `query_len`; `result_type`: `city`/`address`/`place`/`pin`; `rank` | Качество поиска |
| `params_changed` | Значение на «Приборах» подтверждено (экипаж, темп, бюджет, топливо, дата) | `field`; `value_bucket` (§2.4) | Структура экипажей, темпа, бюджета |
| `plan_requested` | Нажата кнопка «ПОЕХАЛИ», план запущен | `km_bucket`; `days`: int; `dog`: bool; `children`: `0`/`1`/`2`/`3+`; `mood` | Каким бывает спрос |

| `hotel_link_clicked` | «Забронировать ночь» нажата, и внешний браузер открыт | `stop_id`; `price_bucket` (§2.4) | Денежная воронка; шаг воронки |
| `excursion_link_clicked` | Нажата ссылка на экскурсию, браузер открыт | `place_id` | Денежная воронка |

относится только к `trip_shared`: у сохранения канала нет.

### 2.3 `trip_driven_confirmed`: новое событие

| Поле | Определение |
| --- | --- |
| Смысл | Пользователь сам подтвердил, что проехал сохранённую поездку (целиком или частично) |
| Когда спрашиваем | После конца поездки E = `start_date` + `days` − 1 (последний день). Вопрос «Вы съездили?» показывается при первом открытии приложения начиная с E + 1 и не позже E + 14 (VAL-04: «Did you go? What went wrong?») |
| Триггер | Ответ «Да, съездили» или «Частично». Ответ «Нет» это событие **не** вызывает |
| Свойства | `trip_id`; `completion`: `full`/`partial`; `days_since_end`: int (дни от E до ответа); `km_bucket`; `dog`: bool; `children`: `0`/`1`/`2`/`3+`; `source`: `in_app_prompt` (сейчас единственное значение) |
| Повторы | Один раз на `trip_id`. В отчёте считаем первое событие |
| Без персональных данных | Без текста ответа «что пошло не так»: свободный текст уходит через `feedback_sent` в бэкенд (ENG-04), не в аналитику |
| Окно для доли | Ответ засчитывается, если пришёл не позже E + 14 дней (§3.3) |

### 2.4 Корзины значений

| Корзина | Границы |
| --- | --- |
| `km_bucket` (длина маршрута) | `<150`, `150-300`, `300-500`, `500-800`, `800-1200`, `>1200` км |
| `total_bucket` (итог путевого листа) | `<10k`, `10-20k`, `20-40k`, `40-80k`, `>80k` ₽ |
| `price_bucket` (цена ночи) | `<3k`, `3-5k`, `5-8k`, `8-12k`, `>12k` ₽ |
| `value_bucket` для `params_changed` | Темп: шаги по 50 км так же, как в приложении (150–900). Бюджет: пресет (`20k` … `80k`, `none`). Экипаж: число взрослых `1`…`7`, детей `0`…`3+`, собака `yes`/`no` |

## 3. Недельная воронка

### 3.1 Определения

- **Учитываемые события:** только релизные сборки и бета (§0, п. 7), без устройств команды.
- **Установка устройства d:** t0(d) = время самого раннего `app_open` этого `device_id`
  во всей истории. Переустановка может дать новый `device_id` и немного завысить число
  установок. Сверка — с установками в консоли RuStore (§3.5).
- **Когорта недели W:** I_W = { d : t0(d) попадает в неделю W }.
- Все множества состоят из **разных** `device_id` (или `trip_id` в §3.3). Повтор события
  не увеличивает счёт.

### 3.2 Воронка устройств: install → plan_succeeded → trip_saved → hotel_link_clicked → trip_driven_confirmed

Шаг засчитывается, если событие случилось в окне от установки **и** устройство прошло все
предыдущие шаги (строгая воронка).

| Шаг | Множество | Окно от t0 | Когорта W закрыта после |
| --- | --- | --- | --- |
| Установка | I_W | — | конца W |
| План | P_W = { d ∈ I_W : есть `plan_succeeded` в [t0, t0 + 7 сут) } | 7 сут | конец W + 7 сут |
| Сохранение | S_W = { d ∈ P_W : есть `trip_saved` в [t0, t0 + 7 сут) } | 7 сут | конец W + 7 сут |
| Клик по отелю | H_W = { d ∈ S_W : есть `hotel_link_clicked` в [t0, t0 + 14 сут) } | 14 сут | конец W + 14 сут |
| Проехал | D_W = { d ∈ H_W : есть `trip_driven_confirmed` в [t0, t0 + 60 сут) } | 60 сут | конец W + 60 сут |

**Доли:**

| Доля | Формула |
| --- | --- |
| Установка → план | r_P = \|P_W\| / \|I_W\| |
| План → сохранение | r_S = \|S_W\| / \|P_W\| |
| Сохранение → клик по отелю | r_H = \|H_W\| / \|S_W\| |
| Клик по отелю → проехал | r_D = \|D_W\| / \|H_W\| |
| Накопленная от установки | c_X = \|X_W\| / \|I_W\| для X ∈ {P, S, H, D} |

**Почему такие окна [решение].** 7 суток: план и сохранение — действия первых дней. 14
суток: отель бронируют между планом и выездом, а по умолчанию выезд в ближайшую субботу
(SPEC §5.3). 60 суток: план на 1–2 месяца вперёд, сама поездка до 4 дней и 14 дней на
ответ. Поездки, запланированные дальше, не теряются: их учитывает поездочная метрика
§3.3.

**Диагностика рядом со строгой воронкой:** охват шага без условия на предыдущие шаги.
Например, H*_W = { d ∈ I_W : есть `hotel_link_clicked` в [t0, t0 + 14 сут) }. Так видно
тех, кто нажал на отель, не сохранив поездку. В строгую воронку они не попадают и
показываются отдельной колонкой.

**Закрытые и ожидающие когорты.** Доля шага X для когорты W выводится, только если на
момент выгрузки окно X закрыто. Иначе в ячейке «ожидает до гггг-мм-дд». В знаменатель
такая когорта не попадает.

### 3.3 Поездочные метрики для таблицы целей (бэклог, «Target numbers»)

T_W = { `trip_id` : первый `plan_succeeded` этой поездки в неделе W и `routing_source` =
`road` }.

| Метрика (цель) | Формула | Когорта W закрыта после |
| --- | --- | --- |
| Запланировано поездок, реальная маршрутизация (≥ 1 000 к W13) | Σ \|T_W\| нарастающим итогом с начала беты | — (накопленный счёт) |
| Доля сохранённых поездок (≥ 25 %) | \|{ τ ∈ T_W : `trip_saved`(τ) в течение 7 сут после первого `plan_succeeded`(τ) }\| / \|T_W\| | конец W + 7 сут |
| Клики по отелю на поездку (SPEC §1: ≥ 8 %) | \|{ τ ∈ T_W : `hotel_link_clicked`(τ) в течение 14 сут }\| / \|T_W\| | конец W + 14 сут |
| Проехавших поездок (≥ 100 к W13) | Число разных `trip_id` с `trip_driven_confirmed`, нарастающим итогом | — (накопленный счёт) |
| Доля подтверждённых поездок | U_W = { τ сохранена : E(τ) в неделе W }, где E = `start_date` + `days` − 1; доля = \|{ τ ∈ U_W : `trip_driven_confirmed`(τ) не позже E(τ) + 14 сут }\| / \|U_W\| | конец W + 14 сут |
| Лист ожидания Pro (≥ 5 % активных) | A = устройства с `app_open` за 28 сут до даты отчёта; доля = \|{ d ∈ A : `pro_waitlist_joined` хоть раз }\| / \|A\| | на дату отчёта |

NPS проехавших (цель ≥ 40) событием не собирается: это опрос VAL-04, считается отдельно.

### 3.4 Исключения и чистота данных

- Когорты до первой бета-сборки не считаются.
- События с `trip_id`, которого нет ни в одном `plan_succeeded`, идут в счётчик ошибок
  данных и в доли не входят.
- Устройства с аномально большим числом событий (больше 500 `plan_requested` за неделю)
  помечаются как возможные боты или тестеры и показываются отдельно. Порог — наше
  допущение, его пересматриваем по данным.

### 3.5 Сверки (каждую неделю, второй независимый способ)

| Число | Сверяем с | Допуск | Если не сходится |
| --- | --- | --- | --- |
| Установки (\|I_W\|) | Установки в консоли RuStore за W | Расхождение показываем; определения разные (магазин считает установку, мы — первый запуск) | Разбор, если первых запусков больше установок |
| `plan_succeeded` | Успешные планы в логах бэкенда (ENG-04) за W | ±5 % | Ищем потерю событий (офлайн, падения) |
| `hotel_link_clicked` | Клики Travelpayouts по sub-id (SPEC §14: sub-id = trip id + stop id) за W | ±10 % | Проверка sub-id, внешнего браузера |
| Сумма по когортам | Пересчёт той же недели другой группировкой (по дням) | 0 расхождений | Ищем строку, на которой расходится |
