# ADR-0003: FastAPI (on Starlette/uvicorn) for the HTTP API

Status: Accepted · Date: 2026-10-23 · Refs: SPEC §11, §12; architecture §10

## Context
The backend serves ~15 JSON endpoints, one SSE stream, needs request validation, an OpenAPI contract for tests and the Android client, and must host the Python planner in-process.

## Decision
Use FastAPI with pydantic v2 schemas (camelCase aliases, `extra="forbid"`), uvicorn (4 workers), SQLAlchemy 2 Core + GeoAlchemy2 column types with psycopg 3 for queries (raw SQL for spatial queries), Alembic SQL-first migrations, Redis for cache and rate limits. Layers: routers → services → (planner, adapters, db); services never import FastAPI. The OpenAPI document generated by FastAPI is the machine contract, tested with schemathesis.

## Consequences
- Fast development, typed validation, automatic OpenAPI.
- FastAPI, SQLAlchemy, psycopg, redis-py, alembic are **not installable in the sandbox now**: API implementation starts in Sprint 2 (or as soon as PyPI is enabled). Starlette + uvicorn + pydantic are present, so the SSE bridge can be spiked now on bare Starlette (optional DEV-020).
- One process type for API; long plans run in a thread pool (limiter 8 per worker) so the event loop stays free.

## Alternatives
- **Bare Starlette** — available now, but we would hand-roll validation and OpenAPI. Rejected for the product; acceptable for a spike.
- **Django + DRF** — heavier, ORM-centric, weak async SSE story.
- **Litestar** — comparable, smaller ecosystem/team familiarity.
- **Go/Kotlin backend** — would split the codebase from the Python planner.
